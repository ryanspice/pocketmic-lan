Current state

What works today

PocketMic v0.1.4 is an early release with real-device validation and honest documentation.

✅ Working

  • 48 kHz mono PCM16 over encrypted UDP
  • AES-256-GCM on every packet
  • QR code pairing (CameraX + ML Kit)
  • LAN receiver discovery
  • Auto-reconnect with discovery resume
  • Voice/Clean/Custom capture modes
  • Wi-Fi lock policy (LOW_LATENCY / HIGH_PERF)
  • EncryptedSharedPreferences for key at rest
  • Session diagnostics with exportable reports
  • Adaptive quality (LinkQualityPolicy — wired in)
  • Windows receiver with voice processing chain
  • One-click default microphone switching

⚠️ Partially working

  • Reconnect state machine — code complete, needs physical testing
  • Version negotiation — UI complete, needs cross-version testing
  • Adaptive quality — wired in, needs real-device validation
  • Android unit tests — pass locally, crash on CI (PATH issue)

❌ Not yet working

  • USB transport (adb reverse) — designed, not implemented
  • PM-LAN virtual audio cable — designed, not built
  • macOS/Linux receiver
  • iOS app
  • Google Play / production-signed APK
  • Opus codec
  • Adaptive jitter buffer with clock-drift resampler

Near-term improvements

v0.2

Make it a real-time system

Planned

  • PM-LAN virtual audio cable — replaces VB-CABLE dependency. Kernel-mode driver with render→capture loopback. Biggest UX win.
  • Opus codec — 48–64 kbit/s VBR, drops bandwidth from 768 to ~64 kbit/s. Needs libopus NDK (Android) and Concentus or libopus P/Invoke (Windows).
  • USB transport — TCP over adb reverse, auto-established. Phone tries localhost first, falls back to Wi-Fi silently.
  • Adaptive jitter buffer — reorder window 3–6 packets, depth 15–200ms, driven by measured jitter.
  • Clock-drift resampler — continuously adjusted resampling ratio. Highest-difficulty item.
  • Capture profiles — implement the Voice/Clean/Custom distinction with proper source detection.
  • Lifecycle state machine — Idle / Armed / Streaming. No mic or socket in standby.
v0.3

Resilience and quality

Planned

  • Dual-path redundancy — first-arrival over USB + Wi-Fi simultaneously. Requires reorder window from v0.2.
  • Adaptive FEC and bitrate — driven by v0.2 telemetry. Never pin FEC at maximum.
  • Oboe/AAudio — move capture to MMAP exclusive. Device supports 2ms burst but current path doesn't use it.
  • Quick Settings tile — one-tap mic toggle from Android notification shade.
  • Companion Device Manager — BLE association for automatic pairing.
  • WebRTC APM / RNNoise — only if measured data shows the light DSP chain is insufficient.

Community

What people ask for

Based on competitor reviews, Reddit threads, and user feedback.

iOS support

The protocol is platform-agnostic. An iOS app is possible but requires Swift/SwiftUI development and App Store distribution. QuicMic's browser-based approach shows it's possible without a native app — PocketMic could add a WebTransport fallback.

Lower latency

Current latency is 100–250 ms. The bottleneck is Wi-Fi jitter, not the app. USB transport (v0.2) would bring this to ~10–20 ms. Oboe/AAudio (v0.3) would reduce capture latency from 4ms to 2ms. Real-time instrument monitoring needs <10 ms — that requires USB.

Opus codec for lower bandwidth

Planned for v0.2. Would drop bandwidth from 768 kbit/s to ~64 kbit/s. The tradeoff: Opus adds encoding latency (~5ms) and complexity (native dependency on Android). PCM stays as a lossless USB-only mode.

No-install browser mode

QuicMic proves the concept: a WebTransport server on the PC + browser on the phone. PocketMic could add this as a lightweight fallback — no app install, just scan a QR code that opens a browser page. Lower quality than the native app, but zero friction.

macOS and Linux support

The protocol is documented and simple. A Python or Rust receiver is feasible. The main gap is the virtual audio cable — macOS needs a CoreAudio driver, Linux needs PulseAudio/PipeWire integration. VB-CABLE-style solutions exist for both.

Multiple phones at once

The protocol supports multiple sessions (each phone gets a unique session ID). The receiver would need UI for selecting which session to play. Not complex, but not a priority until single-phone use is rock-solid.

PC audio to phone (reverse direction)

AudioRelay does this. PocketMic is strictly phone→PC. Reverse direction would need a separate capture path on the PC and a playback path on the phone. Not planned — it's a different product.

Better noise cancellation

Voice mode uses the phone's vendor-tuned processing. Custom mode lets the PC-side DSP do the work. WebRTC APM or RNNoise could be added if the existing chain is insufficient — but stacking DSP on top of vendor processing was the exact problem that made early versions sound wrong.
