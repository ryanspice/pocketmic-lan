Current state

What works today

v0.1.5 is an early release with real-device validation and honest documentation.

✅ Working

  • 48 kHz mono PCM16 over encrypted UDP
  • AES-256-GCM on every packet
  • QR code pairing (CameraX + ML Kit)
  • LAN receiver discovery
  • Auto-reconnect with discovery resume
  • Voice / Clean / Custom capture modes
  • Wi-Fi lock policy (LOW_LATENCY / HIGH_PERF)
  • EncryptedSharedPreferences for key at rest
  • Session diagnostics with exportable reports
  • Adaptive quality (LinkQualityPolicy)
  • Windows receiver with voice processing
  • One-click default microphone switching

⚠️ Partially working

  • Reconnect state machine — code complete, needs physical testing
  • Version negotiation — UI complete, needs cross-version testing
  • Adaptive quality — wired in, needs real-device validation
  • Android unit tests — pass locally, crash on CI (PATH issue)

❌ Not yet working

  • USB transport (adb reverse)
  • PM-LAN virtual audio cable
  • macOS / Linux receiver
  • iOS app
  • Google Play / production-signed APK
  • Opus codec
  • Adaptive jitter buffer

What's planned

Organized by priority. Items move up when measured data justifies them.

Near-term improvements

  • LinkQualityPolicy integration — adaptive prebuffer and concealment ✅
  • Version mismatch UI — clear message when versions don't match ✅
  • Reconnect tracking — elapsed time display during reconnecting ✅
  • Test coverage — 100/100 Windows tests, 22 new quick-win tests ✅
  • Marketing site v3 — merged design, multi-page, social kit ✅
v0.2 Planned

Make it a real-time system

  • PM-LAN virtual audio cable — replaces VB-CABLE. Kernel-mode driver with render→capture loopback.
  • Opus codec — 48–64 kbit/s, drops bandwidth 12×. Needs libopus NDK + Concentus.
  • USB transport — TCP over adb reverse, auto-established. ~10–20 ms latency.
  • Adaptive jitter buffer — reorder window, depth 15–200ms, driven by measured jitter.
  • Clock-drift resampler — continuously adjusted resampling ratio. Highest difficulty.
  • Capture profiles — proper Voice/Clean/Custom with source detection.
  • Lifecycle state machine — Idle / Armed / Streaming. No mic in standby.
v0.3 Planned

Resilience and quality

  • Dual-path redundancy — first-arrival over USB + Wi-Fi simultaneously.
  • Adaptive FEC and bitrate — driven by telemetry. Never pin FEC at maximum.
  • Oboe/AAudio — MMAP exclusive capture. 2ms burst on supported devices.
  • Quick Settings tile — one-tap mic toggle from notification shade.
  • Companion Device Manager — BLE association for automatic pairing.
  • WebRTC APM / RNNoise — only if measured data shows it's needed.

Community

What people ask for

Based on competitor reviews, Reddit threads, and user feedback.

iOS support

The protocol is platform-agnostic. An iOS app is possible but requires Swift development. QuicMic's browser approach shows it's possible without a native app — PocketMic could add a WebTransport fallback.

Lower latency

Current latency is 100–250 ms. The bottleneck is Wi-Fi jitter. USB transport (v0.2) would bring this to ~10–20 ms. Real-time instrument monitoring needs <10 ms — that requires USB.

Opus codec for lower bandwidth

Planned for v0.2. Would drop bandwidth from 768 kbit/s to ~64 kbit/s. PCM stays as a lossless USB-only mode.

No-install browser mode

QuicMic proves the concept: WebTransport server on PC + browser on phone. PocketMic could add this as a lightweight fallback — no app install, just scan a QR that opens a browser page.

macOS and Linux support

The protocol is documented. A Python or Rust receiver is feasible. The main gap is the virtual audio cable — macOS needs CoreAudio, Linux needs PulseAudio/PipeWire.

Multiple phones at once

The protocol supports multiple sessions (unique session IDs). The receiver would need UI for selecting which to play. Not complex, but not a priority until single-phone is rock-solid.

PC audio to phone (reverse)

AudioRelay does this. PocketMic is strictly phone→PC. Reverse direction needs a separate capture path. Not planned — it's a different product.

Better noise cancellation

Voice mode uses the phone's vendor-tuned processing. Custom mode lets the PC-side DSP work. WebRTC APM or RNNoise could be added if measured data shows it's needed.
