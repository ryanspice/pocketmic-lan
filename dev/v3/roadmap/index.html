Current state

Published channels and open acceptance

Stable release · v0.1.5 remains the default Android and Windows download. The development channel is a separate opt-in choice below.

v0.1.6 is a historical source baseline, superseded by the consolidated development release. It is not an upcoming milestone.

Implemented and packaged

  • Android publisher and Windows receiver; encrypted 48 kHz mono PCM16 and negotiated Opus transport
  • Pairing, receiver discovery, desktop audio controls and diagnostics
  • Windows app microphone routing through VB-CABLE, installed separately
  • Stable release v0.1.5 downloads and source

Physical acceptance remains open

  • Named-device audible destination-app routing, sustained sessions and reconnect behaviour
  • Windows Opus audio, live buffering/DSP controls and reversible cable routing
  • Measured end-to-end latency, jitter/loss recovery and battery behaviour
  • Build, package and protocol checks do not establish physical audio acceptance

Apple development previews

  • iOS PCM publisher: existing simulator and unsigned archive workflows
  • macOS receiver and CoreAudio virtual microphone: existing universal build and tester-package workflows
  • Physical iPhone/Mac interoperability, driver installation, routing and recovery still need tester evidence
  • Production signing, notarization, store distribution and TestFlight remain separate decisions

Completed development baseline

Development prerelease · v0.1.7

Published for opt-in development testing, with modern Windows Mica, classic fallback, shared icons, tray and single-instance activation, complete XAML/runtime/Opus packaging, installer preservation and Android pairing/discovery/endpoint fixes.

Recorded build and installation evidence applies to that exact candidate. It does not close every physical audio, device or accessibility scenario.

Roadmap

What comes next

v0.1.8Next bounded development milestone

The next Apple development milestone

  • Physical interoperability — test Android/iPhone PCM with Windows/Mac; Mac currently does not decode Opus v2.
  • Mac driver acceptance — record installation, registration, named-app input, underrun, reconnect, guarded uninstall and recovery.
  • Tester delivery — reuse existing hosted simulator/archive and universal Mac app/driver workflows, with exact artifact hashes and reproducible instructions.
  • Signing decisions — make distribution choices explicit; unsigned previews are not store or notarized releases.
  • Localization — keep Canadian English as fallback; target, translated, reviewed and supported locales remain distinct.
LaterDeferred ideas

Linux, mobile consumer roles and distribution

  • Choose the Linux backend, packaging and virtual microphone approach before implementation.
  • Design Android and iOS consumer roles, pairing and routing before adding reverse audio.
  • Prioritize USB, capture and DSP changes from measured user needs and controlled results.
  • Production signing, automatic updates and wider distribution need their own approved scope and acceptance.

Community

What people ask for

Based on competitor reviews, Reddit threads, and user feedback.

iOS support

The implemented native iOS preview sends PCM v1. Hosted simulator and unsigned archive workflows exist. Physical iPhone interoperability, signed distribution and store availability remain separate acceptance gates for the Apple development milestone.

Lower latency

No end-to-end latency result is established for a representative supported setup. The receiver's 100 ms prebuffer is a setting, not a total latency measurement. We will measure candidate routes before publishing performance targets.

Opus codec for lower bandwidth

The Android source can send negotiated Opus v2, and the Windows receiver supports PCM v1 and Opus v2. Physical encode/decode and end-to-end acceptance are still open. The macOS preview supports PCM v1 only, so choose PCM when testing Android with the Mac receiver.

No-install browser mode

QuicMic proves the concept: WebTransport server on PC + browser on phone. PocketMic could add this as a lightweight fallback — no app install, just scan a QR that opens a browser page.

macOS and Linux support

A macOS receiver and CoreAudio virtual-microphone preview are implemented with hosted universal build and tester-package workflows. Physical installation and routing acceptance remain open. Linux remains deferred pending audio-backend and packaging decisions.

Multiple phones at once

The protocol supports multiple sessions (unique session IDs). The receiver would need UI for selecting which to play. Not complex, but not a priority until single-phone is rock-solid.

PC audio to phone (reverse)

AudioRelay does this. PocketMic is strictly phone→PC. Reverse direction needs a separate capture path. Not planned — it's a different product.

Better noise cancellation

Voice mode uses the phone's vendor-tuned processing. Custom mode lets the PC-side DSP work. WebRTC APM or RNNoise could be added if measured data shows it's needed.
