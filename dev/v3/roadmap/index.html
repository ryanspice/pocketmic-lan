Current state

What works today

v0.1.5 is the current published release. v0.1.6 is in development; hosted builds do not replace physical-device acceptance.

✅ Working

  • Android publisher and Windows receiver in the published v0.1.5 release
  • Encrypted 48 kHz mono PCM16 audio over a private LAN
  • Pairing and receiver discovery
  • Use VB-CABLE, installed separately, to route receiver audio into another Windows app
  • Published release downloads and source: v0.1.5 release

⚠️ Partially working

  • Real-device audio routing, reconnect behavior, long sessions, and timing depend on the device and still need broader field evidence
  • Adaptive buffering is implemented; real-device behavior still needs validation
  • Several Android-to-Windows hardware checks remain open; CI build and unit tests do not prove audible end-to-end audio
  • The Windows PM-LAN route name and third-party VB-CABLE must not be treated as interchangeable

❌ Not yet working

  • macOS receiver and CoreAudio virtual mic are v0.1.6 preview work, not part of published v0.1.5
  • iOS publisher is experimental and not part of the published v0.1.5 release
  • Android Opus selection is in development; physical codec interoperability is not yet accepted
  • Linux receiver and system-wide virtual audio route are planned after v0.1.6
  • Production signing, notarization, store distribution, and TestFlight are not configured as release paths

Roadmap

What's planned

Organized by priority. Items move up when measured data justifies them.

v0.1.5 Released · 2026-09-14

Published Android-to-Windows release

  • LinkQualityPolicy integration — adaptive prebuffer and concealment ✅
  • Version mismatch UI — clear message when versions don't match ✅
  • Reconnect tracking — elapsed time display during reconnecting ✅
  • Current release assets — Android debug-signed APK and Windows receiver archive
  • Validation boundary — CI and unit tests are not evidence of physical audio routing or a measured latency result
v0.1.6 In development · not released

Mac receiver preview, mobile interoperability, and reviewed localization

  • macOS receiver preview — encrypted LAN receive and CoreAudio virtual-microphone path; physical Mac installation and real-app routing must pass before the route is called ready.
  • Mobile publisher interoperability — validate iOS PCM v1 and Android codec behavior against Windows and Mac; incompatible codec modes must be surfaced clearly.
  • Desktop and discovery fixes — complete D1–D5 live acceptance and the authenticated pre-start discovery design.
  • Localization — ship only translated and reviewed locales; default to Canadian English, keep American English distinct, and include Kurdish only when its locale copy passes review.
  • Release evidence — rerun platform CI on one frozen candidate and publish exact artifact hashes and signing status.
  • Release gate — v0.1.6 remains unreleased until physical Mac/mobile checks, product-truth review, and candidate CI pass.
v0.3 Planned

After v0.1.6: Linux and device roles

  • Linux receiver — choose audio backend, distributions, packaging, and virtual-mic approach before implementation.
  • Android and iOS consumer roles — allow phones and tablets to receive from supported publishers after a shared role and routing design is agreed.
  • Expanded device matrix — validate supported Android, iPhone, iPad, Windows, Mac, and Linux combinations with dated evidence.
  • Transport and audio quality — prioritize USB/ADB, capture changes, and DSP from measured user needs and controlled results.
v1.0 Future

Later distribution and scale

  • Signing and distribution — configure and verify platform-specific signing, notarization, store/TestFlight, and installer paths.
  • Upgrade and rollback — define supported migrations and prove clean installation and recovery for each platform.
  • Security and privacy — update disclosures and support materials to match verified runtime behavior.
  • Promotion — widen outreach only after the pilot demonstrates repeatable setup and successful routes.

Community

What people ask for

Based on competitor reviews, Reddit threads, and user feedback.

iOS support

The protocol is platform-agnostic. An iOS app is possible but requires Swift development. QuicMic's browser approach shows it's possible without a native app — PocketMic could add a WebTransport fallback.

Lower latency

No end-to-end latency result is established for a representative supported setup. The receiver's 100 ms prebuffer is a setting, not a total latency measurement. We will measure candidate routes before publishing performance targets.

Opus codec for lower bandwidth

Android Opus support is being validated in the unreleased v0.1.6 source. Codec support and bandwidth depend on the sender/receiver combination; PCM remains the compatibility path where supported. Physical interoperability is still required.

No-install browser mode

QuicMic proves the concept: WebTransport server on PC + browser on phone. PocketMic could add this as a lightweight fallback — no app install, just scan a QR that opens a browser page.

macOS and Linux support

A macOS receiver and CoreAudio virtual-microphone preview are in v0.1.6 development. Physical installation and routing acceptance remain open. Linux receiver support is planned after v0.1.6 and still needs audio-backend and packaging decisions.

Multiple phones at once

The protocol supports multiple sessions (unique session IDs). The receiver would need UI for selecting which to play. Not complex, but not a priority until single-phone is rock-solid.

PC audio to phone (reverse)

AudioRelay does this. PocketMic is strictly phone→PC. Reverse direction needs a separate capture path. Not planned — it's a different product.

Better noise cancellation

Voice mode uses the phone's vendor-tuned processing. Custom mode lets the PC-side DSP work. WebRTC APM or RNNoise could be added if measured data shows it's needed.
