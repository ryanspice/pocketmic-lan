PocketMicTechnical details

For the curious. And the builders.

Local audio.
Open implementation.

The product idea is simple: an Android microphone sends audio to a Windows receiver over a trusted private LAN. Here is what sits underneath — and what the specifications do not prove.

Read the pinned source (opens in a new tab)Get the apps

The audio path.

Android captures 48,000 Hz mono PCM16. The sender places 480 samples into each 10 ms packet, encrypts the audio payload with AES-256-GCM, and sends it to the Windows receiver over UDP.

Documented PocketMic protocol values
Audio format48 kHz · mono · signed PCM16 · little-endian
Packet duration10 ms of captured audio
Audio per packet480 samples / 960 plaintext bytes
Application datagram24-byte header + 960-byte payload + 16-byte GCM tag = 1,000 bytes
Packet rate100 packets per second
Audio payload rate768 kbit/s
Datagram data rate800 kbit/s, before UDP/IP and link-layer overhead

Rate calculation: 48,000 × 16 = 768,000 bits/s for mono audio; 1,000 × 100 × 8 = 800,000 bits/s for the application datagrams. These are protocol calculations, not measured network benchmarks.

A frame is not a benchmark.

The documented receiver starts playback after a 100 ms default prebuffer and trims accumulated buffering above its high-water threshold. The prebuffer is adjustable; concealment and trimming are conservative rather than full adaptive jitter/clock recovery.

10 ms is the audio packet duration.

It is not a measured phone-to-speaker or phone-to-app latency. The release notes leave end-to-end physical-device testing open. This website does not publish a universal delay, quality, range, or battery-life claim.

Capture, without the overpromise.

Voice uses Android’s voice-communication source. Clean requests the least-processed supported input, with device-dependent fallbacks. Neither makes all phone microphones or vendor processing behave identically.

The supplied page also describes Custom mode with PC-side processing, and the supplied Android screenshot shows the selector. Check the actual release’s controls before relying on a particular DSP effect or live-control feature; the release README does not establish the full Custom-mode behaviour described by the page.

Encryption and its boundary.

Documented security and network details
CipherAES-256-GCM authenticated encryption
Pairing-key derivationSHA-256(UTF-8(pairing key))
Nonce constructionRandom 64-bit session ID + unsigned 32-bit sequence
Authenticated dataComplete 24-byte protocol header
Default audio portUDP 49500
Control channelThe next port, per the project documentation. Use the project firewall helper rather than an audio-port-only assumption.
Intended environmentTrusted private LAN only

Use the generated pairing material and treat the key and QR code as secrets. Encryption describes the transport design; it is not an independent security certification.

No internet exposure.

Do not port-forward the receiver. A local encrypted transport is not a hardened internet voice service, and it does not control what your destination app does with the audio.

Build from the pinned source.

The tagged repository stores the project inside pocketmic-lan-v0.1.4/. Start there, not at the repository root. Build prerequisites documented for this version: Android SDK Platform 36, JDK 17+, and .NET 8 SDK.

git clone --branch v0.1.4 --depth 1 https://github.com/ryanspice/pocketmic-lan.git
Set-Location .\pocketmic-lan\pocketmic-lan-v0.1.4
.\scripts\build-android.ps1
.\scripts\publish-windows.ps1

Review scripts before execution and follow your organisation’s PowerShell policy. These are the native app’s build commands, not requirements for hosting this static website.

Firewall helper

# From the native project directory, in elevated PowerShell:
.\scripts\allow-firewall.ps1

Apply only to the trusted Private network profile. Inspect the helper for audio and control-channel rules rather than adding a broad allow-all exception.

What is still a real-world test?

Audio and timing

Phone-to-app latency, capture quality, Wi-Fi stability, and audio-driver behaviour on the user’s hardware.

Install and support

Debug-signed Android distribution, Windows security prompts, driver installation, and device-specific permissions.
